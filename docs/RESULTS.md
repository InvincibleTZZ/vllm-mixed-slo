# 验证记录与失败复盘

## 2026-11-21 的验证条件

同一份 vLLM 0.10.2 官方调度源码用于 CPU 回归和 Linux 项目环境。上游文件的 SHA-256 为 `2bd28fc32cea71370298bb8da0d9a0bbd163ab315b2c6428540131e3999a255f`，本次项目副本安装后为 `081e4b96f4f6966e36530a1e7edf8ae8a6413ba63335c76a816c3b1a24af56de`。在公共环境外复制并安装补丁后，又读取了公共文件，哈希仍与官方值相同。Linux 解释器读取的依赖版本为 PyTorch 2.8.0、Transformers 4.57.1、tokenizers 0.22.2。以上结论分别由文件摘要和 Python 包元数据给出。

## 实施中实际遇到的问题

| 现象与定位 | 本次处理 | 怎样验证 |
| --- | --- | --- |
| 服务器系统 Python 没有 vLLM，从公网索引向项目虚拟环境安装时依赖解析失败。与此同时公共目录有多个 vLLM 版本。仅凭环境名选版本可能将补丁打到不兼容的调度器上。 | 按安装元数据找到 0.10.2，再按上游源码哈希筛选。在项目中建立独立解释器环境，复制 vLLM 包，共用可读的第三方依赖和权重，补丁指向自己的副本。 | 记录公共与私有 scheduler 的 SHA-256，用 `find_spec` 核对实际加载的位置。 |
| 首次在复用公共依赖的 Linux 环境运行全套测试，导入 `scripts.experiment` 失败；本地与干净 CI 没有复现。项目的 `scripts` 原先是隐式命名空间，环境中已安装的同名常规包可以优先命中。 | 添加 `scripts/__init__.py`，让仓库根目录下的入口有明确包边界。 | 从同一项目解释器重新执行全套测试，同时验证 `python -m scripts.experiment --help`。 |
| 同一共享文件系统挂到较旧节点时，Python 启动缺少 GLIBC_2.28。项目内解释器启动后，首次从 PyTorch 请求显存又报 CUDA 初始化失败。 | 私有解释器使用配套的项目内用户态库，系统驱动保持原状。对比初始化顺序后，各 vLLM 进程在首次框架分配前显式初始化原生驱动。 | 在 A800 上分别验证设备枚举、显存分配、结果为 2.0 的矩阵运算以及 vLLM CUDA 扩展导入。详细观测见[运行时移植记录](PORTABILITY.md)。 |
| 初次探测有空闲卡，在真正启动前复查时，这些卡上已经有计算作业。旧的 GPU 快照无法判断两个实验臂是否处在相同条件下。 | 每次服务启动前检查物理卡的 compute PID、显存和利用率。占用冲突的尝试在启动前退出，保留已经完成的实验轮次。 | 端到端性能结论需要同机、同模型、同 trace 的配对记录。未启动的试验不进入分母。 |
| 首次真实校准的 16 个请求全部成功，服务回收后 GPU 已无计算 PID、仅用 1 MiB，但利用率窗口仍报 100%，下一轮被误拒。 | 对“无计算 PID 且显存已回落、仅利用率偏高”最多额外取 4 次样本，间隔 1 秒。保留对真实占卡的拒绝。修正前的校准单独归档，重新启动整套矩阵。 | [占用与释放回归](../tests/test_trial.py)覆盖两个分支。 |
| 正式原生对照第一次启动在 `torch.cuda.set_device` 处报显存不足，尚未接受请求。错误发生在模型权重加载前，已有日志不足以确定当时谁占用了显存。 | 核对 CUDA 与 NVML 的 PCI bus 地址对应同一张卡，重新检测空闲后用原参数 `--resume`。矩阵复用已完成的校准和留出轮次，分别保留失败、成功两个 attempt。 | 第二次原生对照完成 16/16 个请求。公开包中的失败 attempt 记为服务启动失败，单次请求级分母仍取各次实际开始的重放。 |

## R550 节点的部分结果

R550 节点留下了五个完整轮次，分别为两个校准、一个留出、原生关闭和开启采样，共 80 次正式到达。留出集中 26/38 步可查表，其中混合步仅 1/6 可查表。该节点的评测在重新出现其他计算作业后中断，包中保留了原生服务首次启动失败的 attempt。可在离线环境重建相应输入、校准表和已完成轮次的指标。[R550 单独证据包](../evidence/a800-r550-partial/index.json)

## 面试时如何使用这些证据

第一分钟可以用一个具体请求解释预算如何穿过两个分配入口。第二分钟选一个会改变统计结论的反例，例如首个 SSE 数据包包含两个 token 时，客户端无法观测第一个单独 token 的送达时间。最后再讨论只覆盖已见状态的查表策略，以及怎样从独立的 holdout 判断 coverage 和错误放行的代价。具体追问、失败注入和简历措辞见[面试笔记](INTERVIEW.md)。
